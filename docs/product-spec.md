# Skill 管理平台产品方案

这是一个很实用的需求——把 AI 能力（Skill）做成可管理、可分发、可插拔的模块。以下是完整的 Skill 管理功能设计方案。

## 一、核心概念定义

| 概念 | 说明 |
|---|---|
| **Skill** | 一个可独立运行的 AI 能力单元，包含：输入定义、处理逻辑、输出格式、依赖资源 |
| **Skill 市场/仓库** | 存放所有 Skill 的地方，支持版本管理、分类、搜索 |
| **AI 工具/宿主** | 安装并使用 Skill 的载体（如智能客服系统、Agent 平台、内部工具等） |
| **安装（Install）** | 将 Skill 的配置、权限、资源映射到目标 AI 工具的过程 |
| **运行时（Runtime）** | Skill 在 AI 工具中被调用时的执行环境 |

## 二、Skill 的结构设计

每个 Skill 应该包含以下元数据：

```yaml
skill:
  id: "email-classifier-v2"
  name: "邮件意图分类"
  version: "2.1.0"
  author: "fde-team"
  category: "nlp/classification"

  # 功能描述
  description: "自动识别邮件意图：咨询、投诉、售后、合作..."
  icon: "https://..."

  # 输入输出契约
  input_schema:
    - name: "email_content"
      type: "string"
      required: true
    - name: "language"
      type: "string"
      default: "zh"

  output_schema:
    - name: "intent"
      type: "enum"
      values: ["inquiry", "complaint", "after_sales", "cooperation"]
    - name: "confidence"
      type: "number"

  # 运行配置
  runtime:
    type: "llm_prompt"  # 或: python_script, api_call, workflow
    resource: "prompt_v2.1.txt"
    model: "gpt-4o"
    temperature: 0.2

  # 依赖
  dependencies:
    - skill: "text-cleaner"  # 可以依赖其他 Skill
      version: "^1.0.0"

  # 权限
  permissions:
    - "read:email_content"
    - "call:external_api"

  # 评测标准（用于验收）
  evaluation:
    accuracy: ">=0.85"
    latency: "<=2s"
```

## 三、Skill 管理功能模块

### 模块 1：Skill 仓库（Store）

| 功能 | 说明 |
|---|---|
| **发布/上架** | 开发者上传 Skill，填写元数据，上传资源文件 |
| **版本管理** | 支持多版本共存，可设置 latest/stable/beta 标签 |
| **分类与标签** | 按场景（客服/运营/供应链）、技术类型（分类/生成/提取）分类 |
| **搜索与发现** | 支持按名称、标签、使用次数、评分筛选 |
| **审核机制** | 发布前审核：安全性、合规性、效果基准 |

### 模块 2：安装管理（Install）

| 功能 | 说明 |
|---|---|
| **一键安装** | AI 工具从仓库选择 Skill，配置参数后安装 |
| **环境适配** | 自动检查目标 AI 工具的兼容性（模型版本、API 能力） |
| **配置注入** | 安装时允许业务方自定义：模型选择、温度值、阈值、提示词变量 |
| **权限申请** | 安装时自动申请 Skill 所需的权限，需管理员审批 |
| **多环境隔离** | 支持 dev/staging/prod 分别安装不同版本 |

### 模块 3：运行时管理（Runtime）

| 功能 | 说明 |
|---|---|
| **调用监控** | 记录每次调用的输入、输出、耗时、成本 |
| **版本切换** | 运行时热切换 Skill 版本，支持灰度发布 |
| **异常处理** | 调用失败时的重试、降级、告警策略 |
| **资源限额** | 设置调用频次上限、Token 消耗上限 |

### 模块 4：效果评估（Evaluation）

| 功能 | 说明 |
|---|---|
| **内置评测** | Skill 自带评测集，安装后可自动跑分 |
| **业务反馈** | 使用者可对结果点赞/点踩，标注正确/错误 |
| **效果看板** | 准确率、召回率、延迟、成本等核心指标 |
| **自动告警** | 效果跌破阈值时通知 Skill 作者和使用方 |

### 模块 5：资产管理（Asset）

| 功能 | 说明 |
|---|---|
| **交接文档** | 每个 Skill 必须包含：使用说明、边界情况、维护责任人 |
| **依赖图谱** | 可视化展示 Skill 之间的调用关系 |
| **复用统计** | 哪些 Skill 被哪些 AI 工具使用，使用频率如何 |

## 四、安装与使用流程

```
┌─────────────┐     1.发现      ┌─────────────
│  AI 工具 A  │ ───────────────→│  Skill 仓库  │
│  (宿主)      │←────────────────│             │
└──────┬──────┘   2.查看详情    └─────────────┘
       │
       ▼ 3.安装申请
┌─────────────┐
│  配置参数    │  ← 业务方自定义提示词/阈值/模型
│  权限审批    │  ← 管理员确认数据权限
└──────┬──────┘
       ▼ 4.部署运行
┌─────────────┐     5.调用      ┌─────────────┐
│  Skill 运行时 │ ←─────────────│  业务场景     │
│  (沙箱隔离)   │──────────────→│  (客服/运营)  │
└──────┬──────┘   6.返回结果    └─────────────┘
       ▼
┌─────────────┐
│  监控与反馈   │  ← 效果数据回流到仓库
└─────────────┘
```

## 五、关键设计决策

### 1. Skill 的运行方式（三选一或组合）

| 方式 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| **Prompt 模板** | 分类、提取、生成类任务 | 轻量、易维护 | 复杂逻辑难处理 |
| **代码脚本** | 需要数据处理、多步骤编排 | 灵活、可调试 | 需要运行环境 |
| **工作流** | 多 Skill 组合、条件分支 | 可视化、易理解 | 执行效率较低 |

**建议**：支持多种 runtime 类型，由 Skill 作者声明，宿主按需适配。

### 2. 权限与安全

- **沙箱执行**：Skill 代码在隔离环境中运行，限制文件/网络访问
- **数据脱敏**：Skill 只能访问声明过的数据字段，敏感信息自动脱敏
- **审计日志**：谁安装了什么 Skill、什么时候调用的、输入输出是什么

### 3. 版本策略

- **向后兼容**：Minor 版本升级自动推送，Major 版本需人工确认
- **回滚机制**：新版本效果变差时，一键回退到上一个稳定版本

## 六、最小可行方案（MVP）

如果你要快速落地，建议先做这 5 件事：

1. **定义 Skill 标准格式**：一个 JSON/YAML 规范，包含输入输出、提示词、评测集
2. **搭建 Skill 仓库**：简单的列表页，支持上传、版本、分类
3. **做一个安装器**：AI 工具通过 API 拉取 Skill 配置，注入到自身系统
4. **埋点监控**：记录每次 Skill 调用的输入、输出、耗时、业务反馈
5. **跑通一个闭环**：选 1 个业务场景（如客服意图分类），完成从开发→安装→使用→评估的全过程

## 七、与 FDE 工作的结合点

如果你是在准备 FDE 相关的工作，这个 Skill 管理系统可以体现：

- **业务理解**：Skill 按业务场景分类，说明你知道不同部门需要什么
- **最小方案**：从 Prompt 模板开始，不需要一开始就做成复杂平台
- **可验证**：每个 Skill 自带评测集，安装后自动跑效果
- **可交接**：Skill 的元数据、文档、依赖关系清晰，别人能接手
- **资产沉淀**：做好的 Skill 可以被多个业务复用，避免重复造轮子
